1. ELEVATOR PITCH (THE 60-SECOND INTERVIEW SUMMARY)
================================================================================
"I built an enterprise-grade AI Investment Research Assistant that generates
institutional-quality equity research reports, technical market analytics, and
multilingual summaries in seconds.

Architecturally, it is powered by an Autonomous Multi-Agent Team (Agno framework)
governed by an LLM Gateway (LiteLLM) running high-throughput open-source models
(like Llama 3.3 70B via Groq).

Instead of relying solely on an LLM to hallucinate financial math, the system
combines autonomous agentic research with deterministic Python algorithms for
indicators like SMA and drawdowns. It features a multi-tier cache (in-memory +
atomic disk cache) that cut repeat query response times from 10 seconds to 2 milliseconds,
hard tool-budget governors to prevent infinite agentic loops, and a multi-lingual
translation pipeline. The frontend is delivered via an interactive Streamlit dashboard
alongside two standalone CLI utilities."

================================================================================
2. FUNCTIONAL OVERVIEW (WHAT DOES THE APP DO?)
================================================================================
In simple words: It turns any stock ticker (e.g., AAPL, NVDA, TATAMOTORS.NS) into
a complete, verified investment report with actionable insights.

Core User Capabilities:
1. Fast Stock Price Lookup (CLI & Web):
   - Fetches real-time price, currency, daily change, and last market update.
   - Ideal for instant price checks without waiting for full analysis.

2. Comprehensive Investment Research Report:
   - Executive Summary: Company profile, sector, business model, and competitive moat.
   - Key Financial Metrics: Market Cap, P/E ratio, 52-week high/low, EPS, Analyst targets.
   - Latest Market News & Sentiment: Aggregates recent earnings releases, regulatory
     filings, and major developments from DuckDuckGo.
   - Risks & Headwinds: Macro headwinds, valuation concerns, operational challenges.
   - Recommendation & Verdict: Clear Bull / Bear / Neutral perspective.

3. Quantitative Technical Analysis:
   - Calculates 50-day and 200-day Simple Moving Averages (Golden Cross / Death Cross).
   - Computes daily return volatility and Maximum Drawdown over the past year.
   - Renders interactive Plotly price and volume charts.

4. Multilingual Report Translation:
   - Instantly translates full research reports into Hindi (and easily extensible to
     other languages) with intelligent text chunking and localized session caching.

5. Export Options:
   - Download reports directly as formatted Markdown (.md) or clean plain text (.txt).

6. Real-Time LLM Telemetry (Sidebar under Research Setup):
   - Called Tools: Lists every invoked tool with millisecond duration, success/fail icon, and input args.
   - Used Tokens: Micro-breakdown of Prompt, Output, and Total tokens with estimated API costs.
   - Data Flow Steps: Visual step-by-step audit trace from normalization to cache checks, tools, and delivery.
   - Cache Details: Indicates HIT vs MISS, lookup latency in ms, SHA256 key, and estimated tokens saved.

3. ARCHITECTURE & SYSTEM DESIGN
================================================================================
The application follows a Clean 3-Tier Layered Architecture:

[ User Interface Layer ]
   - Streamlit Web App (`streamlit_app.py`)
   - Stock Price CLI (`main-stockprice-only.py`)
   - Interactive Research CLI (`main-with-details.py`)
           |
           v
[ Application / Domain Layer ]
   - ResearchService (`research_service.py`): Orchestrates workflow and caching.
   - Market Data & Technicals (`market_data.py`, `technicals.py`): Pure deterministic math.
   - Multi-Agent Team (`agno.agent`): Specialist agents orchestrated by a Coordinator.
   - Report Formatter & Translator (`report_format.py`, `translator.py`).
           |
           v
[ LLM Gateway & Infrastructure Layer ]
   - LLMGateway (`gateway.py` via LiteLLM): Unified interface to upstream LLMs.
   - Tool Governance: Tool call budgeting, parameter sanitization, tool name aliasing.
   - Caching Engine: Tier-1 memory cache (LiteLLM) + Tier-2 atomic disk cache (`cache.py`).
   - External APIs: Yahoo Finance (yfinance), DuckDuckGo Search, Groq Cloud LLM.

Multi-Agent Collaboration Model:
When a user asks for detailed research, `ResearchService` doesn't just ask one LLM.
It deploys a collaborative Agent Team:
1. Financial Analyst Specialist: Dedicated exclusively to querying Yahoo Finance
   for fundamentals, valuation multiples, and historical price action.
2. Web Research Specialist: Dedicated to DuckDuckGo search for breaking news,
   press releases, earnings transcripts, and market sentiment.
3. Investment Research Coordinator: Receives the synthesized outputs from both
   specialists, performs cross-verification, checks for contradictions, and
   formats the final standardized report.

4. TOOL CALLING DEEP DIVE: AUTONOMOUS VS. LINEAR EXECUTION
================================================================================
Interviewers love asking: "How do your tools work? Is it a hardcoded pipeline (linear)
or does the agent decide on its own (autonomous)?"

The Clear Answer:
"Our system uses a HYBRID MODEL: Autonomous Tool Calling for qualitative research,
paired with Linear Deterministic Execution for quantitative financial calculations."

A. Autonomous Agentic Tool Calling (Where LLMs Excel):
- How it works: We give the agent specialist tools: `YFinanceTools` and `DuckDuckGoTools`.
- Dynamic Decision Making: The LLM autonomously inspects the user query, inspects the
  JSON schema of registered tools, decides WHICH tool to invoke, with WHAT parameters,
  and in WHAT sequence.
- Iterative Reasoning: If the first search query returns insufficient data, the agent
  can autonomously trigger a second search with refined keywords.
- Crucial Safety Mechanism (Tool Call Budgeting):
  Autonomous agents can get caught in infinite tool-calling loops (draining API budgets
  and timing out). We solved this at the Gateway level by strictly enforcing
  `tool_call_limit=5`. If an agent hits 5 tool calls, the gateway forces the agent to
  synthesize its answer using the data collected so far.

B. Linear Deterministic Execution (Where LLMs Fail):
- Why not let the agent calculate SMA or Drawdowns with tools?
  LLMs are notoriously prone to floating-point math hallucinations.
- The Solution: In `technicals.py`, we execute pure, battle-tested Python/Pandas
  code to calculate:
  * SMA-50 and SMA-200 via rolling means.
  * Maximum Drawdown via cumulative maximum and percentage peak drop.
  This is 100% linear, deterministic, and instant (0.001 seconds), giving the user
  rock-solid numbers.

C. Tool Name Aliasing & Normalization (Real Bug Fix):
- Problem: Models like Llama 3.3 on Groq occasionally hallucinated camelCase tool names
  like `<function=searchNews>` instead of the registered snake_case `search_news`. Groq's
  strict API rejected the call with an HTTP 400 error.
- Solution in LLM Gateway: We created alias functions in the gateway tool registry
  (e.g., `searchNews` pointing directly to DuckDuckGo search). If the model hallucinates
  the camelCase variant, the gateway seamlessly resolves it without failing the user request.

5. LLM GATEWAY DETAILS (LITELLM INTEGRATION & GOVERNANCE)
================================================================================
Interviewer question: "Why did you implement LiteLLM as an LLM Gateway instead of
calling Groq or OpenAI directly?"

Answer:
"Direct SDK integration creates severe vendor lock-in, scattered error handling,
and duplicated governance logic. By introducing LiteLLM in `gateway.py`, we created
a centralized control plane for all LLM interactions."

Key Gateway Responsibilities:
1. Vendor Abstraction & Unified Interface:
   - Translates all models to standardized IDs: `groq/llama-3.3-70b-versatile`,
     `openai/gpt-4o`, `anthropic/claude-3-5-sonnet`.
   - Switching providers requires changing ONE environment variable (`MODEL_ID`),
     with zero changes to business logic or prompts.

2. Centralized Tool Budget Governance:
   - Every agent created by `gateway.create_agent()` automatically inherits
     the system-wide `tool_call_limit` (configured via `AGENT_TOOL_CALL_LIMIT`).
   - Ensures no developer accidentally creates an unbudgeted runaway agent.

3. Resilience & Parameter Dropping:
   - Configured `litellm.drop_params = True`: Prevents crashes when switching
     between models that support different parameter schemas (e.g. OpenAI vs Anthropic).
   - Built-in `litellm.num_retries = 2` for transient HTTP 429/503 errors.

4. Offline-Safe & Fast Initialization:
   - By default, LiteLLM attempts to fetch remote pricing maps from GitHub on startup,
     which causes 10-15s timeouts in offline or sandboxed environments.
   - We configured `LITELLM_LOCAL_MODEL_COST_MAP=true` and `LITELLM_TELEMETRY=false`,
     reducing module load time to sub-second.

5. Cost, Token & Execution Telemetry:
   - Extracts exact prompt tokens, completion tokens, and dollar cost estimates
     consistently across providers.
   - Extracts tool execution timings (`duration_ms`), status, and arguments.
   - Tracks data flow steps from input normalization through cache lookups and report delivery.
   - Renders live in the Streamlit UI sidebar under 'Research Setup' via `telemetry_ui.py`.

6. CACHING STRATEGY (MULTI-TIER, ATOMIC DISK, AND TTL)
================================================================================
Interviewer question: "How does caching work and why is it structured this way?"

Answer:
"Financial data and deep LLM research reports are expensive and time-consuming
(5 to 15 seconds per report). We engineered a Multi-Tier Caching System."

The Two Cache Tiers:
- Tier-1: LiteLLM In-Memory Cache (`type="local"`)
  * Stores recent completions in RAM.
  * Retrieval time: < 1 millisecond.
  * Scope: Ephemeral, process-lifetime.
- Tier-2: Atomic File-Based Disk Cache (`ResponseCache` in `cache.py`)
  * Stores structured JSON reports persistently on disk under `data/cache/`.
  * Retrieval time: ~2 milliseconds.
  * Scope: Survives server restarts, CLI sessions, and Streamlit reloads.

Key Engineering Highlights of the Cache:
1. Cache Key Normalization:
   - Keys are computed as MD5 hashes of: `Normalized Ticker (e.g. AAPL) + Scope + Language`.
   - Whitespace and casing are normalized (`" tatamotors.ns "` $\to$ `"TATAMOTORS.NS"`),
     guaranteeing 100% cache hits regardless of user formatting.

2. Time-To-Live (TTL) Expiration:
   - Default TTL is 3600 seconds (1 hour), configurable via `CACHE_TTL_SECONDS`.
   - If an entry is older than 1 hour, it is treated as a cache miss, and fresh
     market data is fetched.
   - Passing `CACHE_TTL_SECONDS=0` completely disables caching (useful for live tests).

3. Atomic File Writes (Crash & Corruption Proof):
   - Traditional file writes (`open('file.json', 'w')`) corrupt the cache if the
     process terminates mid-write or under concurrent access.
   - Our implementation writes to a temporary file (`.tmp.PID`) first, flushes and
     syncs to disk, then performs an atomic rename via `os.replace()`.
   - Even if the app crashes, the cache file remains pristine. Corrupt files are
     auto-detected and safely overwritten.

7. DATA STORAGE, DATABASE, & STATE MANAGEMENT
================================================================================
Interviewer question: "What database do you use, and why?"

Answer:
"We deliberately chose an Atomic Key-Value File-Based Architecture (`data/cache/`)
over a heavy relational or NoSQL database. Here is why:

1. Zero Infrastructure Overhead:
   - No Postgres, Redis, or Mongo daemon to provision, monitor, or pay for.
   - The entire app is fully self-contained and runs with `uv run streamlit run streamlit_app.py`
     or as a single Docker container.

2. Predictable Access Pattern:
   - The workload is 100% Key-Value lookup by ticker symbol. There are no relational
     joins, table scans, or secondary indexes needed.
   - File-system lookup by hash is $O(1)$ and takes < 2 milliseconds on modern SSDs.

3. Streamlit Session State Management:
   - In `streamlit_app.py`, we use `st.session_state` to retain:
     * Current generated report.
     * Calculated technical indicators & charts.
     * In-memory translation cache (switching between English and Hindi is instantaneous
       without re-running the agent or re-reading disk).

4. Data Directory Structure:
   `Investment-Research/`
   |-- `data/cache/`          <-- Atomic JSON files named `<md5_hash>.json`
   |-- `src/investment_research/`
       |-- `gateway.py`      <-- LiteLLM Gateway
       |-- `research_service.py` <-- Core orchestrator
       |-- `cache.py`        <-- Atomic disk cache implementation
       |-- `market_data.py`  <-- yfinance integration
       |-- `technicals.py`   <-- SMA & Drawdown algorithms
       |-- `translator.py`   <-- Multilingual engine
       |-- `settings.py`     <-- Frozen Pydantic/dataclass configuration

8. REAL ENGINEERING CHALLENGES & HOW WE SOLVED THEM
================================================================================
Sharing real debugging stories is the best way to impress an interviewer:

Challenge 1: The "searchNews" Tool Hallucination Bug
- Scenario: A user typed "Tata Motors" and clicked Get Stock Price. The first click
  crashed with: `tool call validation failed: attempted to call tool 'searchNews' which was not in request.tools`.
- Cause: Llama-3.3 on Groq hallucinated a camelCase tool name (`searchNews`) instead
  of `search_news` because the ticker input had spaces ("Tata Motors"), causing the
  model to trigger search instincts.
- Resolution:
  1. Disabled news search on the lightweight price agent (`enable_news=False`).
  2. In the Gateway, added alias mapping for `searchNews` routing to DuckDuckGo news.
  3. Added prompt pre-processing to resolve company names to valid tickers (`TATAMOTORS.NS`).
  4. Enabled automatic retries (`num_retries=2`) in the gateway.

Challenge 2: Sandbox & Offline Delays with LiteLLM
- Scenario: During pytest execution in sandboxed environments, tests hung for 15 seconds.
- Cause: On import, LiteLLM spawned background threads attempting to download GitHub
  model cost maps and send telemetry.
- Resolution: Set `LITELLM_LOCAL_MODEL_COST_MAP=true` and `LITELLM_TELEMETRY=false`
  at module initialization. Test suite execution dropped from 15s to sub-second.

Challenge 3: Multi-Agent Math Hallucinations
- Scenario: The LLM agent provided inconsistent 52-week moving averages and drawdowns.
- Cause: LLMs calculate percentages and moving averages via statistical next-token
  prediction, not arithmetic execution.
- Resolution: Separated qualitative reasoning from quantitative calculation. All
  SMA and Drawdown metrics are computed strictly in Python (`technicals.py`) and
  injected into the final report.

9. TOP 10 TECHNICAL INTERVIEW QUESTIONS & MODEL ANSWERS
================================================================================

Q1: Why did you choose a Multi-Agent architecture instead of a single prompt?
A: "A single prompt trying to do web search, balance sheet analysis, technical math,
and report writing suffers from 'context dilution' and instruction drift. By using
specialized agents (Financial Analyst for numbers, Web Researcher for news, and
Coordinator for synthesis), each agent operates with a focused prompt and a narrow
toolset. This yields significantly higher accuracy and avoids hallucination."

Q2: How do you prevent runaway API costs from autonomous agents?
A: "We implement hard tool call budgets (`tool_call_limit=5`) enforced at the
LLM Gateway level. If an agent loops repeatedly, the gateway caps execution and forces
synthesis. Additionally, our multi-tier cache prevents re-querying identical tickers."

Q3: How do you handle concurrency and race conditions in your disk cache?
A: "We use atomic file replacement semantics. New cache entries are written to a
process-unique temporary file, flushed to disk, and then atomically swapped into place
using `os.replace()`. This prevents reading half-written JSON files if multiple
processes or threads query the same ticker simultaneously."

Q4: How do you handle rate limits (HTTP 429) from LLM providers like Groq?
A: "The LiteLLM Gateway provides automatic exponential backoff retries (`num_retries=2`).
Furthermore, our 1-hour cache absorbs redundant traffic—if 100 users look up NVDA,
only the first user triggers LLM and tool calls; the remaining 99 are served in 2ms
from cache."

Q5: What happens if an external API (like DuckDuckGo or Yahoo Finance) fails?
A: "Our tool integration wraps external requests in defensive try-except blocks. If
DuckDuckGo fails or returns rate limits, the agent logs a warning and gracefully falls
back to fundamental Yahoo Finance data rather than crashing the entire report."

Q6: Why did you use Python dataclasses for Settings instead of simple dictionaries?
A: "We used `@dataclass(frozen=True)`. Frozen dataclasses provide immutability,
type hinting, autocomplete, and prevent accidental mutation of configuration at runtime.
Default values are loaded safely from environment variables with sensible fallbacks."

Q7: What is the purpose of the Report Formatter?
A: "Even with strong system prompts, LLM markdown output can vary. The Report Formatter
validates and enforces standard sections: Executive Summary, Key Financial Metrics,
Technical Indicators, Risks, and Sources. This guarantees a uniform UI experience."

Q8: How does the translation feature avoid making unnecessary LLM calls?
A: "First, if the requested language is English, the translator is an immediate no-op.
Second, translated reports are cached in Streamlit's `st.session_state` and on disk
under a language-specific cache key (`<ticker>_hi`). Toggling back and forth between
English and Hindi is instantaneous."

Q9: How do you test the application without incurring API costs?
A: "Our 20-test pytest suite is 100% deterministic and offline-capable. We mock
external LLM completions and tools, test cache expiration using mocked timestamps,
test math calculations on synthesized pandas DataFrames, and test the gateway with
stubbed agents."

Q10: If you had more time, what would you improve next?
A: "1. Add Semantic Caching with vector embeddings (e.g. Qdrant or Redis) to match
queries like 'Apple' and 'AAPL' semantically.
2. Implement WebSocket streaming for real-time token-by-token report rendering.
3. Add PDF export with styled visual charts.
4. Add user portfolio tracking with daily scheduled email briefings."
